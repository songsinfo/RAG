# 统一业务 Agent 规格

状态：IMPLEMENTING（PR #14 草稿已编码部分功能，UA-01～UA-12 尚未全部验收）。日期：2026-10-09；更新：2026-10-10。
任务清单：[统一业务 Agent Tickets](../delivery/unified-business-agent-tickets.md)。实际状态：[实施进度与剩余验收](../delivery/unified-business-agent-implementation-status.md)。

## 1. 目标与已确认范围

取消用户问答中的普通 RAG / Agent 双模式。所有新问答使用同一个 Agent 循环，由模型选择知识检索或业务工具，必要时组合使用、追问，再依据真实取得的证据回答。不能用一个入口分类器继续把问题分到两套问答编排。

用户明确要求本轮四个业务工具使用假的返回结果，不对接现有 Java 接口。交付目标是可演示、可测试的工具调用与回答闭环，不是实现业务诊断引擎或接通生产服务。

必须提供的能力：

1. 查询这个用户为什么不能使用这张券。
2. 查询到手价的计算规则。
3. 查询这个商品组为什么没有向这个用户出品。
4. 查询这个用户为什么没有命中补贴。

本轮不做：Java HTTP 客户端或接口调研、真实价格/资格计算、多 Agent、独立规划器、业务写操作、通用工具平台。保留文档入库、检索及独立检索评测能力。

## 2. 已核对的代码基础

- [agent.py](../../backend/app/qa/agent.py) 已有 model/tools 循环、`search_knowledge` / `read_section`、运行预算与暂停恢复；扩展现有实现。
- [question_router.py](../../backend/app/qa/question_router.py) 当前只有闲聊、知识问答、不支持请求分类；不能增加 RAG/Agent 路由。
- [router.py](../../backend/app/qa/router.py) 与 [service.py](../../backend/app/qa/service.py) 当前区分 REALTIME 普通 RAG 和 DURABLE Agent；统一新问答需要调整实际执行入口，不只是隐藏前端按钮。
- [claim_validator.py](../../backend/app/qa/claim_validator.py) 校验本次 evidenceId 与文本引用区间；目前具体 gaps 未保留到最终展示结果。
- [context.py](../../backend/app/qa/context.py) 与 [models.py](../../backend/app/models.py) 的来源路径以文档/build 为中心；工具来源需覆盖存储、鉴权、历史、Judge 和展示。
- 前端入口为 [Chat.vue](../../frontend/src/Chat.vue)，共享请求在 [api.ts](../../frontend/src/api.ts)，评测界面为 [Evaluation.vue](../../frontend/src/Evaluation.vue)。

以上是设计依据，不代表新功能已实现或测试通过。

## 3. 统一执行契约

所有新在线问答进入现有 Agent 执行链，沿用 DURABLE Job、取消、预算、SSE 和 checkpoint 机制。前端不再提供 RAG/AGENT 选择。闲聊和不支持请求可以保留廉价处理，但不能形成第二条知识问答链。

知识检索工具 `search_knowledge` 的内部入口由 `RetrievalPipeline.retrieve()` 改为调用现有 [RagRetrievalGraph](../../backend/app/retrieval/rag_graph.py)。外层 Agent 图决定是否检索及何时回答，内层检索图编排 scope、查询准备、Dense/BM25 并行召回、融合、重排与上下文整理；返回可引用的原文、位置和版本，不嵌套生成最终答案。Agent 可只调用一次工具，也可组合知识检索与业务工具；不强制每次都检索、不要求固定调用顺序。

调用检索图时传递当前 actor、run、会话/评估文档范围、检索配置和工具查询参数，保持 ACL、预算、取消检查、阶段事件及 provenance。一次工具调用内的检索节点执行不计为多次 Agent 工具调用；额外模型调用仍计入本次运行预算。沿用检索图现有无持久化 checkpointer 的边界，不声称外层 Agent checkpoint 能恢复检索图的任意中间节点。独立 `/search` 和纯检索评测的底层入口不要求在本轮一起替换。

## 4. 四个模拟工具契约

以下名称与参数是本轮本地演示契约，不声称与真实 Java 接口相同。参数使用明确 ID，不实现名称搜索或身份自动推断。

| 工具 | 必填参数 | 固定模拟内容 |
| --- | --- | --- |
| `diagnose_coupon` | `user_id`, `coupon_id` | 不可用；模拟参与金额 168 元，门槛 200 元；排除商品金额 70 元 |
| `get_final_price_rules` | 无 | 固定演示规则：商品金额先减活动优惠，再检查并扣券，再扣补贴；最低为零；附 200-20-30-10=140 元示例 |
| `diagnose_product_group` | `user_id`, `product_group_id` | 未出品；模拟商品组启用、候选商品存在，但用户地区不在投放范围；明确失败环节 |
| `diagnose_subsidy` | `user_id`, `activity_id` | 未命中；模拟活动有效，但用户不满足新客资格；明确失败条件 |

到手价工具回答“计算规则”，不要求用户先提供购物车，不新增实际价格试算。上述规则和数字全部是演示内容，不表示真实业务规则。模拟金额用整数分记录，代码生成展示文本；模型不负责重新计算。

每个工具返回 `status`、`data`、`mock=true`、`fixtureVersion`、查询对象和 `queriedAt`。结果为固定 fixture，查询对象只回显输入 ID；明确该对象未被真实系统查询。不同失败分支可由测试注入，不通过用户问题中的隐藏关键词触发。

四个工具都应有明确描述、参数 schema 和参数校验。缺必填 ID 时追问，禁止编造 ID；无参数的规则工具可直接调用。未知工具拒绝执行；不得提供模型可自选 URL 的通用 HTTP 工具。无凭据、无网络即可取得模拟结果。

执行错误与业务结果分离：成功取得“不满足条件”是成功执行；超时等模拟执行失败不能当成业务不满足。沿用工具调用预算和重复调用约束，不新增无界重试。

## 5. 上下文、证据与展示

### 5.1 对象和追问

从当前输入及可访问会话历史提取明确对象；当前轮显式 ID 优先。歧义时询问，不把上一个用户的结论用于新用户。保留具体缺失参数的 gaps，并在页面展示可回答的追问。沿用现有会话机制，不引入长期记忆服务。

### 5.2 工具证据

区分 DOCUMENT 和 TOOL 来源；工具结果由代码规范化成证据文本，复用 evidenceId 与引用区间校验，同时持久化结构化快照、工具名、输入对象、查询时间和模拟标志。不能伪造 documentId/buildId，也不能为了支持工具来源而跳过文档 ACL。

实现时选择最小兼容存储方案并提供迁移。证据注册、去重、外发前复核、最终读取、历史引用、Judge 与详情 API 均按来源类型处理。工具快照受当前租户、会话归属与访问权限约束；本轮不声称实现真实业务数据授权。相同工具对不同对象不能错误复用证据。

Agent 和 strict Judge 均只能判断解释是否受返回证据支持；不能将模拟值当作真实业务结论。后续追问引用旧结果时保留查询时间和 mock 标志；不能把旧快照包装成刚刚重新查询。

### 5.3 用户可见结果

所有使用模拟业务结果的回答和来源卡片必须展示“模拟结果，未查询真实业务系统”。该标识由后端结果与前端渲染保证，不仅依赖模型措辞。混合回答区分文档来源和模拟来源。文档仍可定位原文；工具来源展示查询对象、结果、时间和 fixtureVersion，不生成文档链接。

### 5.4 上下文管理与 KV cache

采用“稳定前缀 + 消息追加 + 超阈值集中压缩”。复用现有上下文处理入口，不新增总结 Agent 或长期记忆服务。缓存命中是优化目标，不是正确性或权限的替代条件。

**请求稳定性。** 系统提示词和工具定义按版本固定，工具排列固定；不在提示词前部插入每轮时间、剩余预算或随机 ID。正常循环保留已有消息及其顺序，仅追加用户输入、模型回复和对应工具结果。工具结果首次序列化后不反复重写，原有查询时间、调用 ID 与证据 ID 不变。业务状态更新通过新消息体现，不每轮改写前部快照。稳定序列化只规范首次构造的应用数据，不改变历史模型消息的语义。实际模型/路由变化时不假定缓存可复用。

**有界工具结果。** 工具首次回填前限制大小：保留查询对象、时间、结论、失败条件、必要金额、evidenceId 和 mock 标志，完整结果另存为证据。检索图返回相关片段和准确的原文偏移；不能截断 JSON、破坏引用范围或静默丢弃例外条件。片段不足可沿用章节读取；单个工具结果不能无限增长后再交由全局裁剪处理。

**完整请求预算。** 根据实际模型配置的上下文上限，扣除输出预留和安全余量；输入核算覆盖消息、工具定义及请求中的其他 schema。可用精确计数时优先使用，否则采用保守估算并记录估算方式；模型上限不可用时使用明确配置的保守限制，不把 20000 消息 Token 默认值当作模型容量。每次外发前检查硬上限，Judge、检索图内模型调用也适用各自预算，所有调用仍计入当前 run 的累计预算。

**低频压缩。** 设置高低水位，初始建议为可用消息预算的 85% 触发、压缩到约 60%；这是待验证初值，不是性能结论。未触发时原样保留消息。触发时一次删除较早且不再必要的完整交互组，保留系统约束、当前问题、必要任务状态、未完成工具交互及所需证据；不能拆开 assistant tool_calls 与对应 ToolMessage。若受保护内容无法降到低水位，记录实际压缩结果，避免无进展反复压缩；无法满足硬上限时明确停止或要求缩小问题，不删除当前问题后继续执行。

**状态与上下文版本。** 业务状态保存明确对象、缺失参数、字段来源消息，以及必要结果的证据引用、查询时间和 mock 标志。优先从明确输入和结构化工具结果更新；存在歧义时追问，不通过文本正则猜测用户意图。上下文快照只在初始化或集中压缩时重建，之后追加消息。持久化上下文版本、压缩边界与关联来源，复用现有会话/checkpoint/存储机制并遵守 lease fencing，保证恢复不重复追加。跨提问复用当前会话段的授权上下文，不每次重新拼最近四轮；旧会话可初始化为新版本，初始化历史需修复当前由较早轮次优先占用 4000 字符预算的问题。NEED_CLARIFICATION 问答与待补参数必须能延续，不能因仅加载成功问答而丢失。

**证据和权限不变式。** 压缩快照仍是不可信上下文数据，不升级为系统指令或新证据；保留来源关联，历史 evidenceId 按原 run 解析或显式重新登记，不能当成本轮已存在证据引用。每次外发及恢复仍复核权限和来源版本；撤权/失效时清理或拒绝相关上下文，包括派生状态和快照，即使因此损失缓存。旧诊断不得包装成当前查询。

**缓存观测。** 从模型网关保留供应商实际返回的缓存读取 Token、输入 Token、模型/部署标识、耗时及可用的实际费用；没有字段则记录未知，不当作零命中。记录提示词/工具版本、上下文版本、压缩前后估算量及原因，避免额外明文日志泄露业务内容。缓存参数只在实际供应商和 LiteLLM 链路验证支持后启用，不假设统一 cache key 能补救不同前缀，也不把客户端对象缓存当作 KV cache。缓存比例、输入总量、延迟、费用和回答正确性共同评估，不为命中率保留无用内容或设置未经实测的收益目标。

参考：[OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)。该来源用于解释前缀复用原则，不代表本项目实际模型已启用缓存。

## 6. 兼容与收缩

先扩展工具证据和统一入口，再切换 UI/评测，最后删除不再使用的普通 RAG 问答执行分支。迁移期旧请求的 `mode=RAG/AGENT` 可被接收，但所有新运行都规范化为 AGENT；保留必要的旧字段解析不等于保留双模式。新请求不带 mode 也能工作。

历史运行按原始模式、来源和指标版本读取，不改写历史含义。新完整问答评测统一走 Agent；纯检索评测继续独立运行。旧待执行/恢复中的 RAG 任务须在切换前清点并排空，无法执行的显式终止并记录迁移原因，不静默换语义恢复；没有证据证明已排空时不能删除其兼容执行代码。

本地回滚记录需覆盖代码与数据库兼容性，不能通过回滚丢弃已产生的 TOOL 快照。删除范围仅为已被替代且无引用的普通 RAG 问答编排；必须保留由 `search_knowledge` 复用的 `RagRetrievalGraph`、底层检索模块及纯检索评测。

## 8. 风险与实施边界

主要风险是文档来源假设散布在存储/复核/展示路径，以及旧模式与评测配置残留。实现前需扫描调用点，不能只改工具列表。统一采用现有 DURABLE Agent 后，原普通 RAG 请求可能增加排队开销；验收记录运行阶段耗时，先复用现有 worker，不预设性能改善。

四个 fixture 的业务规则刻意为演示数据；接入真实 Java、真实业务授权和实际规则一致性属于后续范围。本规格不存在必须等待 Java 契约才能开工的任务。
